# 身份与计量的信任边界（stage-1）

依据：project-spec.md §4.1（接入与去重）、§7.3（技术验证第 5–6 条）、§10（身份映射），以及 issue #13 验收标准第 3 条：「明确 GPU 身份去重与计量独立验证的证据来源：不能把 UUID、自报日志或多个签名直接视为物理身份或历史算量真实性证明。」

本文只陈述证据能力边界与剩余信任假设，不宣称任何已被消除的风险。结论分两条独立的信任链：

1. **GPU 物理身份**：链上证据只能支撑「逻辑设备去重」，物理唯一性最终依赖「信任设备所有者 + 多组织人工核验」。
2. **计量用量**：签名与哈希只能证明「谁看过哪些字节」，不能证明「内容真实」；独立重跑测的是重跑那次。剩余信任无法用多签消除，只能用受控重跑抽样压缩。

---

## 1. GPU 物理身份去重

### 1.1 各类证据的能力边界

spec §4.1 原文约束：「设备标识、性能得分或一段签名日志本身，不应被描述为已经证明物理 GPU 唯一性。请明确实际核验证据及其信任假设。」

| 证据 | 取得方式 | 能证明什么 | 不能证明什么 | 伪造/绕过方式 |
| --- | --- | --- | --- | --- |
| NVML UUID | `nvmlDeviceGetUUID` / `nvidia-smi --query-gpu=uuid` | 当前 OS 实例内，驱动为该 GPU 报告的稳定标识符；重装系统通常不变；足以做「同一逻辑设备重复登记」的链上查重 | 物理世界唯一性；数据来源是设备方控制环境里的驱动自报 | mock NVML 响应（Worker 运行在用户控制的 OS 中）；虚拟化/透传下 UUID 行为取决于 hypervisor 与驱动；盗用他机 UUID 抢注 |
| PCI 信息（busId、PCI device id、拓扑） | NVML / sysfs | 本次查询时刻该 OS PCI 拓扑中的位置；型号代号与白名单一致性 | 跨主机唯一性；跨重启/换槽稳定性；内容真实性（同为自报） | 虚拟 PCI 设备；直接伪造 NVML 输出 |
| 自报日志（JSONL 采样、探测报告、执行日志） | Worker 生成并提交 | 操作留痕；内部一致性可事后审计；与链下材料交叉比对的基础 | 任何真实性——攻击者可生成任意内容的日志 | 事后构造、篡改、拼接、重放 |
| 签名文件（设备密钥对报告签名） | Worker 持私钥签名 | 某个私钥持有者对这份字节串签过名；密钥保管得当时提供不可否认性 | 文件内容真实（spec §7.3：三份对同一自报文件的签名不证明该文件真实）；密钥与物理卡的绑定 | 每个「假设备」生成一把新私钥；盗用/代持密钥；密钥与卡的对应关系本身无硬件背书 |
| 性能指纹（标准测试得分、计时分布、每步耗时特征） | 标准算力测试 | 设备性能等级与申报型号大致相符；同型号卡指纹应落在同一区间；可发现「申报 4060 实为更弱卡」一类错报 | 唯一性（同型号两张卡几乎不可区分）；不可被操纵（降频伪装、受控度不足时由另一张更强的卡代跑） | 远程代跑；限频伪装低分/满分复用；把他人结果连同报告整体盗用 |

### 1.2 运行环境攻击面

- **WSL2（当前 stage-1 环境）**：GPU 由 Windows 宿主经 `/dxg` 与用户态库（libcuda、libnvidia-ml）转发。已知风险面：NVML 字段子集可用（功耗/温度/每进程查询常缺失，以 gpu_probe 实测为准）；**Windows 侧进程对 WSL 内 NVML 不可见**——同机 Windows 任务污染「独占执行」假设且无法从 WSL 侧枚举（计量侧影响见 gpu-metering-report.md 第 5 节）；驱动由 Windows 宿主提供，WSL 内无法核验宿主侧配置。
- **虚拟化/透传**：UUID 是否随透传保留取决于 hypervisor 与驱动版本；vGPU/切分场景下一张物理卡可能呈现多个 NVML 设备。首版不承诺覆盖虚拟化身份攻击。
- **重装系统**：物理 UUID 通常不变，链上查重仍能识别「同一卡再次申请」；但「换账户 + 重装 + 谎称新购卡」无法靠 UUID 拦截——识别依赖人工核验与历史比对，而非更强的设备标识。
- **主机/集群重组**：spec §3.1 明确重组不得重复领取接入奖励。这靠「用户 → 集群 → 主机 → GPU」登记层级与历史记录解决，属于登记策略问题，不靠设备标识强度解决。

### 1.3 stage-1 实际采用的证据组合与剩余信任假设

stage-1（`worker/depin_worker/gpu_probe.py` 及后续登记流程）采用的组合：

1. NVML UUID 作为主标识（登记查重键）；
2. `nvidia-smi --query-gpu` 交叉验证（与 NVML 输出互证，两者不一致如实记录）；
3. 名称 / 显存总量 / compute capability 与白名单一致性校验；
4. WSL 多信号判定（/proc/version、WSL_DISTRO_NAME、/mnt/c/Windows、/usr/lib/wsl/lib），把「运行在 WSL」这一计量受限事实写进报告而非掩盖；
5. 每进程查询可用性逐字段探测记录（不可用即记 `unavailable`，不假设可用）。

**剩余信任假设（必须明示，不可由上述组合消除）**：

- A. **信任设备所有者的诚实申报**——所有自报字段（UUID、PCI、日志、签名）产生于所有者控制的 OS 中，mock 驱动或改 Worker 代码即可全部伪造；
- B. **多组织人工核验是物理唯一性的最终背书**——序列号核对、购机凭证、现场或视频检查等链下手段。链上证据链把「重复登记同一逻辑设备」拦下来，把「伪造一个新设备身份」留给人工核验；
- C. 链下材料（发票、照片）无法在链上验证真伪，核验组织只能对「材料与其亲见的一致性」签字，不能对「材料本身为真」无限背书。

这就是 spec §4.1 要求的「实际核验证据及其信任假设」的完整陈述：**stage-1 的去重强度上限 = 链上逻辑查重 + 多组织人工核验，且后者最终仍以信任设备所有者为前提。**

### 1.4 不覆盖的身份攻击清单

| # | 攻击 | stage-1 缓解程度 |
| --- | --- | --- |
| 1 | mock NVML/伪造驱动响应（完全控制自报字段） | 无缓解——只能靠人工核验与 1.3-B |
| 2 | Worker 代码被篡改（跳过采集、伪造计数与日志） | 部分——计量侧靠受控重跑抽查压缩（见 §2），身份侧无自动缓解 |
| 3 | 虚拟机克隆 / vGPU 切分复制同一物理卡为多设备 | 无缓解——首版明确不覆盖虚拟化身份攻击（见 1.2） |
| 4 | 盗用他人 UUID 抢注（先到先得侵占） | 部分——人工核验时发现真实持有人可纠错，但无自动机制 |
| 5 | 同型号卡互换身份（登记卡 A 后物理换成卡 B） | 部分——性能指纹+复测可部分发现，复测规则本身未决（undecided-parameters.md B4/G3） |
| 6 | Windows 宿主侧隐藏 GPU 负载（WSL 特有归因盲区） | 待计量实验实测确认盲区大小（gpu-metering-report.md 第 5 节） |
| 7 | 多账户分时共享同一张卡、对每个账户谎报独立可服务 | 部分——进程/时间线证据可发现重叠，S1/S2 周期未决 |
| 8 | 跨机拼接日志、重放旧证据 | 设计目标为序列号+时间锚定（undecided-parameters.md S5），实现前不覆盖 |

## 2. 计量独立核验

### 2.1 三种工具的数据来源（这是它们可信度差异的根源）

| 工具 | 数据来源 | 能提供 | 不能提供 / 限制 |
| --- | --- | --- | --- |
| ncu (Nsight Compute) | 经 CUPTI 读取 GPU **硬件性能计数器**（per-kernel 指标，如指令执行数、各运算 pipe 的吞吐计数） | 唯一可能满足「硬件实测运算量」口径的来源；按 kernel/算子粒度归因；可区分不同 pipe 的指令类别 | 需要计数权限与驱动支持（WSL 下待实测）；部分指标需 kernel replay（改变执行行为、引入额外执行）；不区分「业务执行」与「测量引起」的额外运算需靠会话设计 |
| NVML | 驱动**自报**的整机状态：利用率、显存、功耗、时钟、进程列表 | 执行时间线佐证：任务窗口内利用率/显存形态与申报计数是否量级一致；进程存在性 | 不是运算计数；不区分精度/算子；粗粒度采样；同样产生于设备方可控环境 |
| torch.profiler | 记录算子调用与张量 **shape**，FLOPs 由已知公式从 shape **推导** | 与 ncu 计数交叉验证量级；发现漏计（推导值远大于实测值时报警）；结构化算子清单 | 本质是理论推导——spec §7.1 明确「性能分析工具的公式估算不能标为硬件实测」；本项目中它永远只能作交叉核对，不得作为计费值 |

### 2.2 核验组织能独立取得什么、如何检查

| 独立证据 | 取得方式 | 能证明 | 不能证明 |
| --- | --- | --- | --- |
| 受控重跑计数基线 | 核验组织在场（现场或受控远程会话）用同版本模板、同输入摘要、同计量规则版本重跑 | 该卡该环境完成该任务所需的运算量量级区间；自报计数是否落在合理区间 | 原始那次的真实用量——spec §7.3：「独立重跑测到的是重跑那次的运算，不自动证明原始提供者过去消耗了多少」 |
| NVML 时间线比对 | 核验组织自行采样（或调取带签名的时间线并抽查复采） | 自报执行窗口与独立利用率/显存/进程形态是否一致；「空窗期申报满载」一类粗矛盾 | 精确用量；Windows 宿主侧负载（WSL 盲区，见 1.2） |
| 材料完整性与绑定 | 核对文件哈希、订单绑定、规则版本、签名覆盖（设备签名 + 各组织签名绑定同一摘要，spec §3.2） | 三个组织看过同一份字节；材料与订单的对应关系成立 | 文件内容真实（见 2.4）——「三份对同一自报文件的签名不证明该文件真实」（spec §7.3 原文） |

### 2.3 必须信任设备方的部分（无法用上述证据替代）

1. 原始执行确实发生过，且计数器采集路径未被篡改（ncu 本身、其输出文件、Worker 上报链路都运行在设备方环境里）；
2. 宿主上没有隐藏负载或被隐藏的进程（尤其 WSL 的 Windows 侧，WSL 内 NVML 枚举不到）；
3. 计量材料由真实运行的 Worker 生成，而非事后构造；
4. 设备驱动/运行环境未被定制为系统性少报计数器。

### 2.4 必须写进每一份核验文档的三句话（spec §7.3 的直接结论）

1. **三份对同一自报文件的签名只证明三个组织看过相同字节，不证明该文件真实**——多签提高的是「所见一致」的置信度，不是「内容为真」的置信度。
2. **文件哈希一致不证明 AI 计算正确**——哈希只绑定内容，不评估内容。
3. **独立重跑测到的是重跑那次的运算量**——它是基线与一致性证据，不是原始执行的历史证明。

因此「链上多签 + 哈希」**不能单独**作为「硬件计量已可信」的证明；首版可信度上限 = 抽样受控重跑 + 时间线一致性 + 人工核验的叠加，且仍保留 2.3 的剩余信任。抽样比例与差异容忍区间本身是未决参数（undecided-parameters.md M3）。

### 2.5 与集中部署的关系

stage-1 采用单 orderer + 单 peer 集中开发部署（见 decision-log.md B1）：六组织身份齐备但运行在同一台开发机上。此时 2.2 表中的「各组织签名」来自**同一管理主体控制下的身份**，按 spec §3.2 只算「角色与流程隔离」，不构成相互独立的管理主体背书——即集中部署下这些签名连「三个独立主体看过」都不成立，仅验证流程与权限逻辑本身。任何安全声明不得引用 stage-1 部署作为独立核验证据。

## 3. 摘要：剩余信任的最低限度

| 信任链 | 链上/自动证据能到达的上限 | 最终仍需信任 | 对应未决项 |
| --- | --- | --- | --- |
| GPU 物理身份 | NVML UUID + 交叉验证 + 白名单一致性 + 登记历史 → 拦截「同一逻辑设备重复登记」 | 设备所有者诚实 + 多组织人工核验（1.3-A/B） | G2、G3、B4 |
| 计量用量 | ncu 硬件计数 + NVML 时间线 + 受控重跑基线 + 材料绑定 → 把伪造空间压缩到容忍区间内 | 原始执行真实性、采集路径未被篡改、宿主无隐藏负载（2.3） | M1–M4、O5、V5 |

若 stage-1 计量实验（gpu-metering-report.md）显示硬件计量或独立证据要求无法满足，按 spec §7.3：提交具体缺口、最小替代方案及其改变的信任假设，等待业务确认；不得将缺口方案称为已达到真实结算要求。

## 后记：计费口径变更后的信任边界更新（2026-09-13，D1）

计费改为「模板工作单元」后（decision-log.md D1），计量信任假设相应变化：

- **不再需要**：硬件计数器读数的可信性（ncu 类证据从计费前置条件中移除）。
- **仍然需要**：(1) 模板执行的真实性——交付结果由真实训练/推理产生（固定 seed 的
  loss 曲线、可数输出是主要证据）；(2) 工作单元数与结果一致——核验组织可从交付物
  独立复算（数样本/读曲线），这比"信任自报计数文件"弱化了设备方的自证成分；
  (3) Worker 环境未被篡改（恶意执行环境可伪造 loss 曲线——与原口径下伪造计数文件的
  风险同级，多组织抽检与同型号设备对照复算是缓解手段，成本待定，关联 V1/V2）。
- **已验证的支撑证据**：真实负载三精度训练 loss 可复现（实验 b，固定 seed）、
  停止延迟与进程时间线可观测（实验 f/d）——这些继续服务于执行真实性与预算保护。
