# Coding Agent 完整启动提示词：基于 Fabric 的 AI 算力共享原型

你是一名负责端到端交付的工程师。请根据下面的完整需求，在现有仓库中设计并实现一个基于 Hyperledger Fabric 的 AI 算力共享网络原型。如果仓库为空，创建最小可维护的项目结构。

本文包含已经确认的业务规则、供你自行选择的工程实现，以及尚未确认的参数和技术可行性问题。请严格区分三者。不要重新询问已经确认的问题，也不要把未确定的值或无法验证的能力自行补成既定规则。

## 1. 项目目标与首版规模

让用户把自己的 NVIDIA GPU 接入网络，绑定到用户账户，为其他用户执行预置 AI 任务，并通过 Fabric 链码管理奖励、预算托管、任务核验、付款和退款。

首版是可以真实运行的小规模原型，使用少量 NVIDIA GPU，例如几张 RTX 4060。准确型号、数量、机器分布和驱动环境需要检查实际环境，不能假定已经有八卡服务器、昂贵专业卡或大型集群。

重点是跑通真实闭环：

设备接入与测试 → 多组织核验 → 接入奖励逐步解锁 → 发布任务并托管预算 → 调度并真实执行 → 整单核验与验收 → 一次结算或全额退款。

保持架构简单，不引入实现这个闭环不需要的微服务、大型调度平台、公链、交易所、真实货币支付或任意代码执行平台。

Fabric 是联盟链。多组织共同管理账本与核验规则，计算由参与者设备提供。不要声称首版实现了匿名、无需准入、完全无需信任的公共算力网络。

## 2. 已确定的规则与已作废的方案

以下最终版本具有优先级：

- 使用 Hyperledger Fabric，由链码定义并执行关键业务规则。
- 每张物理 GPU 单独登记；主机、集群和用户之间建立归属关系。
- 新 GPU 接入后，按标准算力测试得分获得接入奖励额度。
- 接入奖励与测试得分成正比，按累计合格可服务时间逐步解锁，累计 168 小时全部解锁。
- 【变更 2026-09-13，决策记录 docs/stage1/decision-log.md D1】任务按**模板工作单元**计费：每个模板声明计费工作单元（训练按 step，批量推理按 batch/token/输出样本数，以模板计量字段为准）与单价表；单元数以交付结果可复算为核验口径。不按资源占用时长、利用率积分或固定报价收费。原「按硬件实测 GPU 运算量计费，不同精度不同权重」口径废止（硬件计数在可控环境全部受阻，且单元复算核验性更好）。
- 价格与工作单元定义随模板版本与订单锁定，执行中不得单方变更。
- 发布者支付的任务代币全部分配给提供算力的用户，平台不抽成。
- 普通用户之间不允许自由转账。
- 任务正常核验由三个组织参与，至少两个同意。
- 争议由另外三个未参与该次初始核验的组织处理，至少两个同意即可裁决。
- 只支持平台预置的训练与批量推理任务。
- 优先把一个任务完整放在同一提供者的集群内；需要跨提供者集群时，必须在启动前取得发布者同意。
- 发布任务时一次托管预算上限。
- 任务启动后连续执行，结束后整单验收、一次结算。
- 执行失败或因预算不足终止，托管预算全额退款，提供者本单收入为零。
- 正常核验通过后，发布者有 24 小时确认或提出异议；到期无异议视为同意。
- 任务收入在链上结算后立即可用。

以下早期方案已作废，不得重新实现为首版规则：

- 按用户发放固定初始代币。
- 全网从启动起永远固定代币总量。
- 按任务固定报价或按 GPU 占用时长直接收费。
- 阶段交付、阶段验收、阶段付款、等待上一阶段批准再继续计算。
- 失败任务按已经完成的阶段收费。
- 分段续费、预算耗尽后等待用户充值恢复执行。
- 由原核验组织处理该次核验的争议。

早期讨论过“每阶段自动重试一次”，但阶段机制已经取消。这不能自动转换成“整单自动重试一次”。不要因此增加运行中的重试、迁移或恢复产品流程；如确实需要自动重试，应单独提出规则。整单执行故障目前按已确认的失败退款规则处理。

## 3. 用户、GPU、集群与组织

### 3.1 用户与设备

同一个用户可以同时发布任务和提供算力，可以绑定多张 GPU，也可以管理多台主机组成的集群。

资源登记层级应能够表达：用户 → 集群 → 主机 → 物理 GPU。

每张物理 GPU 是接入登记、去重和接入奖励的单位。八卡服务器包含八张独立登记的物理 GPU；重新组合主机或集群不能重复获得这些卡的接入奖励。

计算 Worker 不必同时运行 Fabric peer。不要把“一个 GPU”映射成“一个区块链组织”。

### 3.2 核验与仲裁组织

设备接入与任务正常核验均采用三个组织、至少两个同意的门槛。争议使用另外三个组织、至少两个同意的门槛。

同一次事件中，初始核验组织集合与仲裁组织集合必须互不重叠，至少需要六个可承担相应职责的组织身份。每个组织最多计一票，不能用同一组织的多个用户或证书凑票。

投票必须绑定同一个设备申请或订单、证据摘要、结果版本及核验结论。不能把对不同用量报告的签名拼成一个多数。

开发部署可以提出把这些逻辑组织放到同一台开发机上的简化方案，但必须在文档中区分“角色与流程隔离”与“真实管理主体独立”。集中部署不能作为真实独立核验的安全证明。

组织选择、成员准入、提供者及发布者的利益冲突回避、组织退出替补、核验和仲裁费用来源尚未确定。不要暗中扣除用户任务费用来支付组织，因为全部任务费用归算力提供者的规则已经确定。

## 4. GPU 接入、算力测试与奖励解锁

### 4.1 接入与去重

GPU 必须属于已经验证的 NVIDIA 型号白名单，完成接入测试并达到多组织批准门槛后，才具备领取接入奖励的资格。

标准算力测试用于确定性能得分，设备身份核验用于防止重复领取。这两个问题必须分别解决。

防止同一 GPU 通过更换账户、重新安装 Worker、重装系统或变更集群重复领取。设备标识、性能得分或一段签名日志本身，不应被描述为已经证明物理 GPU 唯一性。请明确实际核验证据及其信任假设。

设备所有权转移、显卡更换、退役和性能复测引发的奖励变化尚未确定。先保留身份和奖励历史，不能默认为这些操作触发重新发放。

### 4.2 奖励金额

每张卡的奖励额度满足：

    接入奖励额度 = 统一奖励系数 × 标准算力测试得分

测试得分翻倍时，奖励额度翻倍。不要改成按人头发币、按固定档位发币或递减奖励函数。

测试脚本、标准工作负载、得分单位、测试时长、精度组合及奖励系数尚未确定。请提出与实际 GPU 和计量能力匹配的最小方案，不直接把 GPU 型号标称峰值当成实测得分。

### 4.3 可服务时间

奖励按累计合格可服务时间解锁：

- GPU 通过可用性检查并开放可用资源。
- 空闲时应接受符合预先公布条件的匹配任务。
- 执行本网络任务的时间也累计。
- 离线或不满足条件时停止累计，已有进度保留。
- 恢复合格服务后继续累计，不重新归零。
- 累计达到 168 小时后，该次接入奖励全部解锁，不能继续无限产生接入奖励。

仅上报在线状态不等于已经证明可以服务。需要定义最低限度的可用性验证，但不引入用户运行中操作。

时间记录必须防止重启、重放、重复上报造成重复累计，也不能在无证据的离线间隔自动补计时间。采样周期、合格证据、拒单条件、宽限期、解锁粒度和具体释放曲线尚未确定。“168 小时全部解锁”不等于已经决定线性逐秒释放。

不得擅自加入离线罚没、重新计时或回收已解锁奖励的规则。

## 5. 代币、余额与守恒

代币是本应用链码管理的内部记账资产，不是 Fabric 自带的原生币，也不对接真实货币。

已取消按人发固定额度。新 GPU 通过规则获得接入奖励，所以代币供给可以随新增合格 GPU 及奖励发行过程增加，不要求全生命周期固定总量。

任务流程本身必须守恒：预算托管、付款、退款不增发、不销毁代币，不能收取平台抽成。已发行总量应能与所有可用余额、托管余额及其他已发行锁定余额核对一致。

尚未确定“接入时铸造并锁定”还是“先授予奖励额度、解锁时铸造”。请把奖励额度、已发行供应量、已解锁金额区分清楚，提出一种一致的账务方案等待确认，不能在两个阶段各发一次。

普通用户没有自由转账接口。用户可以通过提供算力获得任务收入，余额不足时不能创建超出可用余额的预算托管。已结算任务收入立即可用，不附加争议期冻结或保证金。

金额与运算计数应使用确定性的整数或精确有理数表示。代币最小单位、数值范围、精度权重的分母、取整与余数分配规则尚未确定，必须提出能保证资金守恒的具体方案。

测试环境可以有隔离的测试余额 fixture，但不能把任意给账户铸币的开发接口作为正常业务发币入口。

## 6. 任务形式与调度

### 6.1 模板任务

首版支持平台预置训练任务和批量推理任务。用户选择模板，提供模板允许的数据、参数、资源需求和预算，不提交任意 Shell、任意 Python 程序或任意容器镜像。

具体模型与数据集尚未指定。可优先提出一个适合少量 RTX 4060 级 GPU 的小型模型，同时演示训练和批量推理，例如小型图像分类模型。此处是工程建议，不是已经选定了模型和验收阈值。

订单应固定模板版本、允许的参数、模型与输入摘要、精度配置、资源需求、预算、价格和计量规则版本。执行中不得由任意一方单方面改变。

必须真实训练或推理。随机输出、sleep、空循环或固定返回值不能冒充实际 AI 工作。

训练可以在内部保存故障诊断或最终结果所需的检查点，但不把检查点做成运行中的用户验收、付款或续费节点。

### 6.2 集群优先

优先选择同一提供者的一个集群完整承接任务。资源要求包括可用卡数、单卡显存、型号兼容性和任务需要的通信条件；不能只看全网卡数总和。

例如用户请求八张卡时，优先选择能完整提供八卡资源的集群，而不是直接拆成八个分散单卡节点。该例不意味着首版必须准备八张卡。

若没有单个集群能满足需求，只有在发布者启动前明确同意、且模板与实际网络支持的情况下，才可跨提供者集群执行。记录参与者、资源分配及发布者的同意。

少量 GPU 的首个实际用例可以从单卡任务开始，但不能因此宣称已验证跨集群协同。跨集群应通过小规模真实测试验证；若硬件或通信环境不具备条件，明确保留该分支为未完成或受阻功能，不静默删除已确认要求。

完整集群之间的排序、排队期限、GPU 独占或共享、通信阈值及不接受跨集群时的等待行为尚未确定。不要为此引入复杂优化算法；先提出简单、可解释的方案。

## 7. 硬件计量、统一价格与收益分配

### 7.1 计量要求

【变更 2026-09-13，D1】收费目标是任务实际执行、符合计费定义、经过核验的**模板工作单元数**（训练 step / 推理 batch、token、样本数），不是运行时长、利用率积分、设备峰值乘时间，也不是仅根据模型规格推导的理论 FLOPs。硬件运算量计数（ncu 类）从计费前置条件降级为可选的执行真实性研究。

首版只收 GPU 运算费。CPU、内存、存储和网络暂不单独收费，但可以提出合理的资源额度和结果保留期。

不同运算精度分别计数，使用不同权重换算统一计费工作量。具体支持的精度、操作集合、Tensor Core 与普通算子的计数关系、FMA 算几次、稀疏计算和整数运算的处理尚未确定。

性能分析工具的公式估算不能标为硬件实测。硬件指标覆盖不足、计量权限缺失或无法归因到订单时，不能悄悄用另一种计费口径替代。

### 7.2 费用表达

按模板工作单元计费（变更 2026-09-13，D1），统一按以下关系实现：

    C = Σ_u (price_u × N_u)
    R_i = Σ_u (price_u × N_i,u)    （Σ_i N_i,u = N_u）

其中：

- u：该订单模板声明的计费工作单元类型（训练模板为 step；批量推理模板为 batch / token / 输出样本数，以模板计量字段为准）。
- price_u：模板版本中该单元类型的单价（整数最小代币单位，随订单锁定）。
- N_u：该订单通过核验的实际完成单元总数；以交付结果可复算为准（推理输出可数、训练曲线含 step 数与固定 seed，核验组织可独立重算）。
- N_i,u：提供者 i 完成并通过核验的单元数；同一用户多张 GPU 的贡献汇总到该用户。
- C：成功订单的最终总费用（要求 C ≤ B，退回 B − C）。
- R_i：提供者 i 的收入。

多提供者成功订单按各自完成并通过核验的单元数分配费用；只有一个提供者时，其获得全部任务费用。不另外加入按显卡型号报价、竞价、供需动态价格或平台分成。精度（fp32/fp16 等）不再作为计费权重维度——它是模板执行配置的一部分，由模板版本声明。

在代币最小单位下，最终分配必须精确满足 Σ_i R_i = C。如何取整和分配余数须有明确、确定性、可测试的规则。

价格和权重应随订单锁定版本，不能因后续配置更新追溯改变既有订单。具体价格、权重及更新权限仍待确认。

### 7.3 必须先做的技术验证

【变更 2026-09-13，D1】本节验证从计费前置条件降级为**可选的执行真实性研究**（已完成的部分见 docs/stage1/gpu-metering-report.md：负载真实性、进程归因、停止延迟实测通过；硬件计数受阻如实留档）。计费核验以工作单元结果复算为准，不再要求本节的硬件计数闭环。

（历史要求，保留作参考）先在实际 GPU 上验证一个小型真实 AI 工作负载，输出：

1. GPU 型号、驱动、系统、执行环境及可用计量权限。
2. 使用的硬件计数工具、原始指标、单位、覆盖范围和转换规则。
3. 是否能区分所需精度与算子类别，如何归因到任务和参与 GPU。
4. 测量开销，是否需要重放，以及如何区分业务执行与测量引起的额外执行。
5. 同机其他任务、空操作、重复执行或伪造报告是否会污染计量。
6. 核验组织实际取得什么证据、如何检查，以及哪些部分仍需信任设备所有者。
7. 对每项能力给出“实测通过／未覆盖／受阻”，不能只列工具名称。

计量重放、预热、初始化、通信算子及执行故障造成的额外运算是否收费，尚未全部确定。先分别记录，不把所有硬件活动直接并入用户账单。

GPU 身份可信性和用量可信性也是两个独立问题。三份对同一自报文件的签名不证明该文件真实；文件哈希不证明 AI 计算正确；独立重跑测到的是重跑那次的运算，不自动证明原始提供者过去消耗了多少。

如果实际设备不能满足硬件计量或独立核验证据要求，提交具体缺口、最小替代方案及其改变的信任假设，等待业务确认。继续开发不受此问题阻塞的链码、接口和明确标记的测试流程，但不得将有缺口的方案称为已达到真实结算要求。

## 8. 整单执行、预算保护与失败规则

### 8.1 发布与托管

发布者设置预算上限 B。链码确认可用余额足够后，在一次有效交易中创建订单并全额托管 B。

不能透支、欠费、自动追加预算或从账户额外扣款。资源领取和执行资格必须校验；Worker 等待相关交易有效提交后才开始执行，不能把收到交易 ID 当成已经成功。

### 8.2 连续执行

启动后连续执行至完成，运行中不安排用户确认、阶段组织核验、阶段结算、续费或人工恢复流程。

保留必要的后台计量、日志、故障检测和预算保护。预算接近上限时预留停止执行所需的额度并结束任务，不暂停等充值，不继续无上限计算。

停止预算保护必须考虑采样和停止延迟。无论实际执行成本怎样变化，都不能超出托管预算向发布者收费；如果当前计量方式无法支持可靠的预算预警，明确报告技术缺口。

### 8.3 结束后的资金处理

- 整单成功且满足验收或有效仲裁依据：按最终核验费用 C 付款，要求 C ≤ B，退回 B − C。
- 整单执行失败：全额退回 B，所有提供者本单任务收入为零。
- 因预算不足终止：全额退回 B，所有提供者本单任务收入为零。
- 不支付部分成果，不支付“此前已完成的阶段”，不向发布者转嫁失败尝试费用。
- 本单失败退款不等于扣回提供者已经获得的其他收入或接入奖励，不擅自引入罚没。

提供者承担失败任务已经发生的计算成本。这是已确认规则，不得因为成本看起来不利而自行改成按已运行量收费。

无论失败是否发生在跨集群任务的一部分，只要整单执行失败，对发布者执行整单退款。提供者之间的额外赔偿或责任追偿没有确认，首版不能自动扣款实现。

执行失败与“执行已完成但结果有争议”必须分开。对已交付结果的异议走核验和争议流程，不能允许发布者随意把它标成执行失败而直接退款。

## 9. 整单核验、24 小时验收与独立仲裁

### 9.1 正常核验

提供者执行完成后提交整单结果、结果摘要、计量材料及各 GPU／各提供者贡献记录。三个核验组织依据同一版本的模板标准核验计量与成果，至少两个认可一致的证据和结论才算正常核验通过。

模板验收必须描述任务是否完成的可执行标准。训练文件存在不自动证明训练有效，结果哈希一致也不自动证明工作正确。不要自行添加用户未约定的训练准确率或损失阈值。

### 9.2 发布者验收

以下条件全部成立后，开始 24 小时验收计时：

- 最终成果可供发布者访问和下载。
- 验收材料齐全且绑定到该订单。
- 至少两个正常核验组织已经通过。

处理方式：

- 发布者明确接受：可按核验金额结算。
- 发布者在期限内提出具体异议：进入争议，保持相应资金托管。
- 期限内既无确认也无异议：到期视为同意，允许结算。

不能从 GPU 停止运行或提供者首次上传的时刻提前启动计时。不能在正常核验未通过、结果不可访问或已进入争议时触发默认同意。

### 9.3 争议仲裁

由另外三个未参与该次初始核验的组织检查订单、模板规则、结果、计量证据及双方说明。至少两个同意才能形成有效裁决。

裁决可以替代发布者确认，依据规则决定付款或退款。普通用户、单个组织或管理员不能绕过门槛直接释放资金。

不能由初始核验组织复核后充当该次争议的仲裁多数。裁决必须绑定同一份具体决定，防止对不同退款金额或用量结论的签名被拼接。

核验超时、仲裁超时、无多数、申诉次数、计量证据被推翻后的纠正流程尚未确定。先列出这些未决转移，不能暗中用“管理员直接改余额”或“超时随便退款”填补。

## 10. 最小工程架构建议

先检查仓库说明、环境和现有实现。除 Fabric 外，以下是推荐工程选择，不是必须使用的已确认业务规则：

- Go 链码与 Go API 服务，通过 Fabric Gateway 交互。
- Python Worker 与预置 AI 执行器。
- 简单 Web 前端，可用 Svelte；优先复用仓库现有框架。
- 一个简单的文件／对象存储服务保存输入、模型、证据和结果。
- Docker Compose 管理适合容器化的开发组件；实际 GPU Worker 支持在独立机器运行。
- 一个进程内模块化后端即可，不强制把注册、调度、计费等拆成微服务。

链上保存身份关联、设备与奖励记录、订单与预算、计量和结果摘要、核验票、验收／异议／仲裁决定，以及余额变动。

链下负责 AI 计算、文件存储、高频心跳、日志、计量采集与证据检查。不要让链码执行 AI、调用外部 HTTP、读取设备或处理高频监控数据。

订单和资金以账本为准，链下数据库是索引或缓存。需要说明事件重复投递、服务重启和索引重建的处理。

链码超时不会自行触发。由后台任务提交到期处理交易，链码验证状态、时间依据与权限。不要在链码中使用节点各自的本地墙钟作为确定性裁决依据，也不能把客户端任意填写的时间当成不受约束的可信时间。提出简单、可审计的时间与可服务时长证明方案。

用户登录身份、Worker 凭据和 Fabric 身份必须有可信映射，不能相信请求体里的 userId、owner 或 orgId。不允许所有操作共享一个管理员身份。

至少为普通用户、设备所有者、正常核验组织和仲裁组织实施权限检查；每一类关键余额变更都应有明确来源。

## 11. 状态、接口和页面

采用最小整单状态机。可以用“等待调度、执行中、等待核验、等待发布者验收、争议中、已结算、失败已退款、预算终止已退款”等状态表达；具体枚举和接口由你设计。

在实现前给出每个状态转换的调用主体、前置条件、资金变化、资源释放条件、幂等键及异常路径。不要加入按阶段执行的状态机。

资源分配必须避免同一 GPU 在不允许共享的情况下被重复承诺。任务领取、结果提交、投票、付款、退款、奖励解锁、超时处理必须防重放和重复执行。不同终态不能分别触发付款和退款。

建议页面：

- 我的设备：GPU、主机和集群、登记核验状态、得分、可服务状态、奖励额度与解锁进度。
- 算力市场：真实资源能力、可用情况和模板支持情况。
- 发布任务：选择模板、参数、数据、资源需求、预算；必要时在启动前确认跨集群执行。
- 任务详情：整单状态、日志、结果、核验状态、费用、24 小时验收期限、接受／异议操作。
- 账户：可用代币、托管代币、接入奖励额度与已解锁金额、任务收入和流水。
- 核验与仲裁入口：严格按组织身份显示可执行操作，可采用简洁页面或 CLI。

页面要读取真实业务状态。开发测试 mock 必须隔离、明确标记，不能让未通过的硬件计量或未实现的跨集群功能显示为已验证。

## 13. 开发顺序与交付要求

按下面的工程里程碑推进。它们是开发顺序，不是用户任务执行中的业务阶段。

1. 检查仓库和实际硬件，整理已确定规则与当前阻塞项，完成单 GPU 真任务计量与证据可行性实验。
2. 完成身份、GPU 登记与去重、标准测试报告、接入批准、奖励额度和解锁账务；经济参数未确认时仅用隔离测试验证。
3. 完成整单订单、预算托管、资源领取、真实模板执行、结果提交、核验和验收。
4. 完成一次结算、失败与预算终止全额退款、24 小时默认同意、独立组织仲裁。
5. 接入简洁前端，完成少量 GPU 的真实端到端演示，并验证已具备条件的集群与跨集群路径。

每一步都交付可运行代码和明确的验证结果，不要只产出架构文档或页面。允许为阻塞项搭建隔离测试桩，但如实保留缺口，不能以模拟结果宣布全部完成。

交付：

- 完整源代码、实际兼容的依赖版本和配置示例。
- 环境检查、Fabric 启动与链码部署、账户与组织准备、GPU Worker 启动脚本。
- 简洁 README 和从新环境启动的操作步骤。
- 架构、链上／链下边界、整单状态机、资金流和权限说明。
- 硬件计量实验报告、身份与独立核验的信任假设和未覆盖范围。
- 业务决策记录、待确认参数清单和验证／未验证功能清单。
- 可重复的正常任务、失败退款、预算终止、验收超时和独立仲裁演示步骤。

## 14. 必须通过的关键验证

为关键资金规则、状态竞争和真实集成编写有意义的测试，避免只有实现镜像或截图。

至少验证：

1. 同一 GPU 不能通过重复申请、换绑或 Worker 重启重复获得接入奖励；验证不能覆盖的身份攻击如实记录。
2. 相同性能得分产生相同奖励，奖励与得分按统一系数成正比。
3. 合格服务时间累计、离线暂停、恢复继续；累计 168 小时不会超发；重复上报不重复解锁。
4. 余额不足不能托管预算，普通用户不能自由转账、擅自铸币或修改他人资源。
5. 少量真实 GPU 能接入并执行真实训练、批量推理，产出可检查的模型／结果和计量材料。
6. 需要跨集群时没有发布者事先同意不能启动；单集群优先逻辑可验证。
7. 成功订单按已核验的模板工作单元数计费（变更 2026-09-13，D1），提供者收入总和等于任务费用，剩余托管余额完整退款；单元数可从交付结果复算。
8. 执行失败和预算不足终止均全额退款，提供者本单收入为零，没有部分成果付款。
9. 一个组织的多张证书不能凑成两票，对不同证据的投票不能合并。
10. 未达到正常核验门槛不能启动验收期限；结果不可用不能提前计时。
11. 发布者确认可触发结算；24 小时无异议允许默认同意；期限内异议阻止自动结算。
12. 仲裁组织集合与初始核验集合不重叠，至少两票形成裁决，单组织不能强制付款。
13. 重复事件、重复请求、付款／退款竞争、验收／超时／争议竞争不能导致重复转账或两个终态。
14. 任务资金路径不增发不销毁，所有供应量变化均能追溯至接入奖励的已确定发行规则。
15. 没有阶段验收、阶段结算、分段续费或运行中的人工介入依赖。
16. 硬件计量与独立证据未验证时，系统和文档不能宣称可可信结算；测试 mock 与真实验证结果明确分开。

完成后，请按“已经实现并实际验证、已实现但未验证、明确受阻、仍待用户确认”四类报告结果，并给出最短复现步骤。不要为节省时间把部分实现描述成完整交付，也不要为了追求大型平台形态扩大首版范围。

现在开始：先检查仓库与可用环境，给出简短实施计划和当前最重要的可行性检查，然后推进已经授权、可独立完成的工作。
